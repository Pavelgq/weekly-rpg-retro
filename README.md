# Weekly RPG Retro 🎲

A Claude skill that turns weekly reflection into an RPG campaign: you are the
character, Claude is the Game Master. Under the hood — the classic agile
retrospective structure (five stages, checking last week's action items,
experiments against recurring problems). On top — lore, stats, bosses, and
achievements, so the ritual is one you want to repeat instead of abandoning
after a month.

The GM speaks whatever language you speak.

## What it looks like

Once a week you tell Claude "let's run my weekly session". The Game Master:

1. reads your character sheet, working supports, and feedback; resumes an
   unfinished session and checks last week's experiments;
2. asks relevant questions one at a time, skips what you already answered,
   and lets you choose a focus; RPG language is light rather than compulsory;
3. separates your reported events from its hypotheses, proposes stat deltas
   using agreed criteria, and notices both difficulties and what helped;
4. helps you pick 1–3 small quests for the coming week;
5. closes with a grounded observation and a validated, recoverable save.

## Core mechanics

**Personal stats.** Keep 4–6 user-defined stats and symbolic game points.
Each has explicit included behaviors, exclusions, scoring anchors, and a criterion
version. Changes apply going forward; old scores retain their original meaning.
Points do not measure health, burnout, objective competence, or personal worth.
Illness, external delays, and missing information do not earn penalties. Legacy
vital alerts are retired without rewriting the campaign's history.

**Bosses.** A recurring difficulty has a stage and history:
**Spotted → Studied → Fighting → Retreating → Defeated**. Missing news is
explicitly "no fresh data", never worsening or a clean week. Levels rise only
with fresh, user-confirmed evidence of increased impact or frequency; neither
silence nor a recurrence automatically increases them. External waits receive
brief factual updates. Choose focus by current relevance, not the highest level.

**Working supports.** `supports.md` records what actually helped, the conditions,
limitations, and source session. Reuse those observations when choosing actions.

**Correctable GM.** Interpretations are hypotheses until checked. Corrections
and preferences go into `gm_feedback.md` and are read next time. Fixing an AI
mistake does not automatically become the user's achievement.

**Small experiments.** Each quest names a trigger, action, minimum success,
likely obstacle/adaptation, and review session. If it did not happen, change the
tactic around the actual obstacle rather than asking for more willpower.

**Closing the loop.** Every session starts with the fate of last week's quests.
"Not done" is material for observation, not for guilt: the campaign's Prime
Directive is that the character acted in the best way they could given what
they knew, the resources they had, and the state they were in.

**Quarterly review.** Every ~12 weeks — the view from above: progress on the
main quests, how fast bosses get defeated, the rating trend, the shift in how
the character speaks about themselves, and next quarter's goals.

## Installation

A skill is a folder with a `SKILL.md`. Put it where your Claude looks for
skills:

- **Claude Code**: `.claude/skills/weekly-rpg-retro/` inside the campaign
  repository (or `~/.claude/skills/` for all projects);
- **File-capable chat / Cowork**: install the whole skill folder using the host
  application's skill support. A lone pasted `SKILL.md` lacks the save helper.

## Important: the campaign needs a folder

The skill describes the process, but the state (profile, character sheet, week
logs) lives in files. Create a dedicated directory or repository for the
campaign — and run sessions where Claude can reach it: Claude Code, Cowork, or
a chat with a connected GitHub repository. In a plain chat with no file system,
the campaign won't survive between conversations.

The structure the skill maintains on its own:

```
my-campaign/
├── profile.md            # setting, goals, values, your stat set
├── character_sheet.md    # current state: stats, bosses, achievements
├── supports.md          # working supports with evidence
├── gm_feedback.md       # corrections and conversational preferences
├── achievements.md      # achievement history
├── history.csv          # numeric history generated by the save helper
├── .retro/sessions/     # drafts and completed source records (private)
├── week1_log.md          # one log per week
├── week2_log.md
└── quarter1_review.md    # quarter summaries
```

See [`examples/`](examples/) for a fictional sample profile and week log that
show the intended tone and format.

## Quick start

1. Create an empty campaign folder/repository and install the skill.
2. Tell Claude: **"Let's set up my campaign"** — the Game Master runs
   onboarding (~20 minutes): a setting to your taste, main quests for the
   quarter, your values, known adversaries, your personal stats.
3. A week later: **"Let's run my weekly session."** Full format ~30 minutes,
   short ~15.

The skill never launches itself — only when you ask.

## Philosophy

- A retrospective that never checks past decisions is an empty ritual.
- Bosses describe a recurring difficulty, not a character flaw.
- Lore is packaging: use it when helpful; no insight or metaphor quota.
- Unknown is not failure, and game points are not a psychological assessment.
- A small quest doable under any shape of week beats a big plan.

## Reliable saving and validation

Install the **whole skill folder**, including `scripts/` and `references/`.
The save helper uses Python 3.9+ on macOS/Linux, with no third-party dependencies.
It checkpoints drafts, checks dates and stat totals, rejects conflicts, and
recovers interrupted multi-file saves without duplicate history rows. It does
not promise that all files change atomically at the same instant.
See [persistence workflow](references/persistence.md). If execution is unavailable,
the GM preserves a portable draft and reports that a validated save is pending.
Campaign data stays in your chosen folder; using a cloud model still sends the
conversation to that provider. Do not commit personal logs to this skill repo.

Developer checks:

```sh
python3 -m unittest discover -s tests -v
```

Run the [behavioral scenarios](evals/scenarios.md) as actual conversations as well;
passing script tests does not establish coaching quality.
